# 家人授权关系持久化设计

## 目标

将当前前端模拟的家人关联流程推进为后端可持久化的授权关系，同时保持现有个人 Dashboard、家人页面、健康助手和模拟手环数据不变。第一阶段只解决“谁可以查看谁”，不把模拟指标冒充为真实设备数据。

## 范围

- 新增 `family_relation` 关系表。
- 每个用户拥有独立关联码；用户可展示自己的码，家人输入该码发起关联。
- 查询接口只返回当前登录用户已授权的关系。
- 支持解除关系和更新授权状态。
- 所有接口沿用 JWT 鉴权和统一 `Result` 响应。
- 前端暂保留本地演示数据，待接口稳定后再切换数据源。

不包含设备绑定、实时指标落库、家人端同意流程、AI 会话持久化和真实邀请码生成服务。

## 数据模型

`family_relation`：

- `id`：主键。
- `owner_user_id`：发起查看的一方。
- `member_user_id`：被授权家人。
- `relationship`：称谓，例如父亲、母亲。
- `invite_code`：目标用户的独立关联码，服务端只按精确值匹配；用户之间不可重复。
- `status`：`ACTIVE` 或 `REVOKED`。
- `created_at`、`updated_at`：审计时间。

使用 `(owner_user_id, member_user_id)` 唯一约束，避免重复关联。查询时必须同时限制 `owner_user_id = 当前 JWT 用户` 和 `status = ACTIVE`，不能接受前端传入的 owner id。

## 接口

- `GET /api/family/relations`：查询当前用户的有效家人关系。
- `GET /api/family/invite-code`：查询当前登录用户自己的关联码。
- `POST /api/family/relations`：提交 `{ inviteCode, relationship }`，服务端解析目标用户的独立关联码并创建关系。
- `DELETE /api/family/relations/{id}`：撤销当前用户拥有的关系。
- `PATCH /api/family/relations/{id}`：更新当前用户拥有关系的称谓或状态。

目标用户不存在、重复关联、关系不属于当前用户、邀请码为空时返回明确业务错误，不泄露其他用户是否存在的额外信息。

## 数据流

登录用户携带 JWT 调用接口。控制器通过 `SecurityUtil` 获取当前用户 ID，服务层校验参数和关系归属，Mapper 只执行带 owner 条件的查询与更新。助手远程请求继续只接收前端传入的已授权上下文；在前端切换真实关系数据前，不改变助手行为。

## 错误处理与兼容

- 旧的本地固定邀请码仅作为离线演示兼容，不作为真实关联码；后端未启动时前端可回退本地模式。
- 数据库初始化失败时不影响个人 Dashboard 构建，但后端关系接口返回服务错误。
- 不返回邀请码原文之外的敏感账户字段，不返回未授权家人的健康数据。

## 验收标准

1. 每个用户都有独立关联码，关联码唯一且不能通过接口改成他人的码。
2. 数据库可创建关系表并通过唯一约束阻止重复关系。
3. 未登录访问五个接口均被 JWT 拦截。
4. 用户 A 不能查询、修改或删除用户 B 的关系。
5. 有效关系可查询，撤销后不再出现在查询结果中。
6. Maven 测试和打包通过，现有数据隔离测试不回归。
7. 前端现有家人页面和健康助手行为不改变。
